## 1. 概述与术语

### 1.1 硬件概览

| 项 | 值 |
|---|---|
| 主控 | 恒玄 BES2800HP（双核 M55 + NPU） |
| 存储 | SCY 64GB eMMC |
| 无线 | **仅 BLE，无 Wi-Fi 硬件** ⛔（任何"Wi-Fi 快传"设想不成立） |
| 音频编码 | Opus，84 B/包，单声道，20ms @ 48 kHz（SILK WB，TOC 0x4B/0x48，config 9） |
| BLE 吞吐（实测） | ≈20 KB/s ⇒ 32 kbps 音频约 5 倍速；1 小时录音传输 10–12 分钟 |

### 1.2 术语表

| 术语 | 含义 |
|---|---|
| **App / 客户端** | 手机端（Nomily AI），GATT 中央角色 |
| **卡** | DingTalk A1 录音卡，GATT 外设角色 |
| **secret** | 32 字符 hex 字符串（≈128-bit 随机数），**烧在卡内**，鉴权唯一凭据。与账号/绑定关系无关 |
| **did** | deviceId 字符串（如 `"1046161310"`），自证会话身份。鉴权只认密钥不认 did，但**鉴权后所有命令必须携带同一个 did** |
| **fid** | 文件 ID = 该录音的开始时间戳（Unix 秒）。也是实时流 `0x0117` 的会话标识 |
| **帧（frame）** | 一次完整协议消息（8 字节头 + 载荷），可能跨多个 BLE 写入/通知到达 |
| **包（packet）** | 84 字节的 Opus 编码单元（20ms 音频） |

### 1.3 角色与通道拓扑

```
        ┌─────────────── BLE (GATT FE3C) ───────────────┐
        │                                               │
   App (central)                                     卡 (peripheral)
        │ ── write FE1C（请求 0x13 / ACK 0x31）──────▶ │
        │ ◀── notify FE1B（响应 0x31 / 推送 0x14）──── │
```

- **控制面**：JSON 载荷（UTF-8）。
- **数据面**：二进制载荷（文件块、索引表、实时音频、诊断日志）。

## 2. 传输层：广播与 GATT

### 2.1 广播识别 ✅

```
-60 dBm  DingTalk A1   svc=[FE3C]
         mfg=[0001b5000d7a2b9ed600000567303635350101000000]
```

| 规则 | 说明 |
|---|---|
| 广播名 | `DingTalk A1` |
| 服务 UUID | **短格式 `FE3C`**。过滤必须用 `contains("FE3C")`；`hasPrefix("0000FE3C")` 会匹配失败 ✅ |
| 厂商数据 | 含 `g0655` 段 = **SN 尾 4 位**（`30 36 35 35` = ASCII "0655"），用于多卡区分与凭据匹配 |

### 2.2 GATT 特征 ✅

| 特征 | 属性 | 说明 |
|---|---|---|
| `FE1C` | read, write, write-without-response | App → 卡方向。read 回 `"Hello Datapath demo\0"`（固件调试残留） |
| `FE1B` | read, notify | 卡 → App 方向。read 回上一次命令的响应缓存 |

- 大块传输优先 write-without-response；发送前必须检查 `canSendWriteWithoutResponse`（见 §5.9 流控）。
- MTU：连接后协商；吞吐瓶颈 = MTU + 逐块 ACK。下载日志应记录 `MTU payload nnn B` 便于排查。

## 3. 帧层 Framing

### 3.1 帧头布局 ✅（8 字节，大端）

| 偏移 | 长度 | 类型 | 字段 | 说明 |
|---|---|---|---|---|
| 0 | 1 | u8 | `type` | `0x13` 请求（App→卡）· `0x31` 响应/ACK · `0x14` 卡主动推送事件 |
| 1 | 2 | u16 BE | `cmd` | 命令码（`0x0008` / `0x0100` / `0x0117` …） |
| 3 | 1 | u8 | `seq` | 序号；**ACK 必须沿用被应答帧的 seq**（见 §3.3） |
| 4 | 4 | u32 BE | `len` | 载荷长度；**帧总长 = 8 + len** |
| 8 | len | bytes | `payload` | JSON（UTF-8）或二进制 |

### 3.2 分包重组 ✅

BLE 通知是流式的，一帧可能拆成多个通知到达，也可能多帧粘连。**必须按 `len` 重组**后再解析（参考实现 `DingTalkA1Framer`）：缓冲所有到达字节 → 读头 8 字节 → 取 `len` → 攒满 `8+len` 才交付一帧 → 剩余字节留给下一帧。

### 3.3 ACK 应答规则 ✅（违反即断传输）

对卡主动推送的帧（`0x0114` / `0x0115` / `0x0116` / `0x0117`），App 的应答帧必须是：

```
type = 0x31，seq = 被应答帧的 seq，payload = {"code":200}
```

⛔ 用 `type=0x13` 应答会被卡当成**新命令**处理（回 405）并中断当前传输。

## 4. 会话与鉴权

### 4.1 流程 ✅

```
App                                        卡
 │ ── 0x13 cmd=0x0008 {"did":"","corp_id":""} ──▶  （免鉴权，did/corp 可传空）
 │ ◀── 0x31 {"code":200,"random":"<32 hex>"} ────
 │
 │  token = hex( AES-128-CBC(
 │      key = ASCII(secret 的前 16 字符),   ← ⛔ 不是 hex 解码后的字节！
 │      iv  = key（同上）,
 │      pt  = ASCII(random), padding = none ))
 │
 │ ── 0x13 cmd=0x0133 {did, corp_id, model, sdk_ver, token} ──▶
 │ ◀── 0x31 {"code":200, ...能力位} ─────────────  会话建立
 │
 │ ──（此后每条命令 payload 必须带同一个 did）──
 │ ── 0x13 cmd=0x0134 {"did": ...} ──▶            断开会话（每次用完必须发）
```

参考 JSON（`0x0133` 请求）：

```json
{
  "did": "1046161310",
  "corp_id": "",
  "model": "Windows_A1_Client",
  "sdk_ver": "V2.1.3",
  "token": "<128 hex 字符>"
}
```

### 4.2 鉴权算法要点 ✅

| 规则 | 说明 |
|---|---|
| key 来源 | `secret` 是 32 字符 hex **字符串**；key = 其 **ASCII 前 16 字节**。⛔ 先 hex-decode 再当 key 是错的 |
| 填充 | **无填充**（key/pt 各 16 字节，恰好一个 block） |
| 挑战一次性 | ⛔ 再发一次 `0x0008`，上一个 `random` **立即作废**（最新覆盖） |
| 挑战保密性 | 挑战-应答不泄露 secret（secret 永不出卡；AES-128 已知明密文对对穷举 2¹²⁸ 无增益） |

### 4.3 会话规则 ✅

| 规则 | 依据 |
|---|---|
| 鉴权**只校验密钥，不校验账号**：错 `did` → 200、错 `corp_id` → 200 | P3/P4 实测 |
| 鉴权后**每条命令必须带同一个 did**（换了/没带 → 405）；`0x0100` 的 `set` 分支同样必须带 | P6 实测 + 2026-10-18 真机踩坑 |
| 卡上**没有账号归属**；二手卡唯一门槛是 secret。隐私上仍应先解绑（否则录音会同步进原账号的钉钉） | — |
| 会话按连接缓存：同一 BLE 连接内鉴权一次即可；**405 = 会话丢 token**，恢复方法见 §4.4 | — |

### 4.4 鉴权错误处理 ✅

| code | 含义 | 客户端处置 |
|---|---|---|
| 200 | 成功 | 继续 |
| 405 | **未鉴权**（会话丢 token） | 清除本地"已鉴权"标志 → 重跑 `0x0008 → 0x0133` → 重试原命令**一次** |
| 501 | 凭据不匹配（token 算错 / 用了别卡的 secret） | 提示用户重新导入密钥；不要自动重试 |
| 502 | token 形状非法（非 hex / 长度错） | 客户端代码 bug，非凭据问题 |
| 503 | 字段缺失 / null | 同上 |

> 卡端校验顺序 = **先形状后密码学**：形状错 502/503，形状对值错 501。没有跳过校验的调试分支（已穷举验证）。

### 4.5 `0x0133` 回包能力位 ✅

| 字段 | 值 | 含义 |
|---|---|---|
| `cap_remark` | 2 | **支持打点**（配合 §5.10 的 `0x0B000001` 事件） |
| `cap_voiceprint` | 1 | 声纹 |
| `cap_incognitomode` | 1 | 隐身模式 |
| `cap_aikey_option` | 1 | AI 按键回报值 1000 |
| `cap_schedule` | 2 | 卡内定时任务 |

## 5. 消息规范

> 通用约定：除 `0x0008` 外，所有 App→卡命令的 payload 都必须包含 `"did"`。响应统一 `{"code": <int>, ...}`，`code` 语义见 §4.4 / 附录 B。

### 5.1 `0x0008` getRandom（取随机挑战）✅

| 项 | 值 |
|---|---|
| 方向 | App → 卡 |
| 鉴权 | **免鉴权**（白名单成员之一） |
| 请求 | `{"did":"", "corp_id":""}`（可传空串） |
| 响应 | `{"code":200, "random":"<32 hex 字符>"}` |

用途：鉴权第一步（§4.1）；也用作**免凭据验活探针**——`0x0008` 回 32 hex 且 `0x0132` 回 405，即可判定"卡活着且是这套协议"。

### 5.2 `0x0133` connectDevice（鉴权）✅

见 §4.1 / §4.5。响应含能力位；会话按连接缓存。

### 5.3 `0x0134` disconnect（断开会话）✅

| 项 | 值 |
|---|---|
| 方向 | App → 卡 |
| 请求 | `{"did": "..."}` |
| 说明 | 每次读/传完成后**必须发送**，干净释放会话（也是实验纪律：用完即断） |

### 5.4 `0x0132` getStatus（状态查询）✅

| 项 | 值 |
|---|---|
| 方向 | App → 卡 |
| 请求 | `{"did": "..."}` |
| 响应 | JSON（字段见下） |

响应关键字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `audio_status` | int | 录音状态（`0x0100 start` 后以此复核，**不要信 0x0100 的 200 就当已开录**） |
| `duration` | int | 当前/最近录音时长 |
| `fid` | int | **最近文件指针**（fid 游标，增量拉取用；也等于实时流的会话标识） |
| `storage_used` / `storage_free` | int | 单位 **MB，不是字节** ⚠️ |
| `battery_percent` | int | 电量百分比（充电状态**不在此处**，见 §5.10 `0x0100000C`） |
| `version` | string | 固件版本 |

其他用途：空闲保活（参考实现空闲 20 s 后发一次）；`0x0110` 索引前的游标来源。

### 5.5 `0x0100` recordControl（录音控制）✅

| 分支 | 请求 payload | 说明 |
|---|---|---|
| 开始 | `{"did":"...","action":"start","params":[]}` | 回 200 后**必须再发 `0x0132` 复核 `audio_status`** ✅ |
| 停止 | `{"did":"...","action":"stop","params":[]}` | 同上 |
| 设置 | `{"did":"...","action":"set","params":[{"key":"upload_stream","val":0 或 1}]}` | **实时流开关**；⛔ `set` 分支也必须带 did（漏带 → 405，症状"实时页点录音没反应"） |

> 🔶 已知 `0x0100` 还可携带 `incognitomode` / `aikey_option` 参数（未实现）；`0x0137` stream_record 回 200 但**不推流**——实时流唯一开关是 `upload_stream` ⛔。

### 5.6 `0x0110` 文件索引（响应为二进制）✅

| 项 | 值 |
|---|---|
| 方向 | App → 卡（请求 JSON），卡 → App（**二进制响应**） |
| 请求 | `{"did":"...", "s_fid": <起始fid>, "e_fid": <结束fid>, "recently": <bool>}` |

响应二进制布局：

| 偏移 | 长度 | 说明 |
|---|---|---|
| 0 | 2 | `code` u16 BE |
| 2 | 2 | 条数 u16 BE |
| 4 | 8 × N | 每条 8 字节：`[0:2]` 标志 · `[2:6]` fid u32 BE · `[6:8]` 状态 |
| 尾部 | — | `0x5A` 填充 |

空表响应示例：`00 C8 00 00 00 00 00 00 5A 5A 5A 5A`。

⛔ **索引条目里没有文件大小**。`size` 的权威来源是 `0x0114` 下载属性帧（§5.7）。客户端内部对索引条目的 `sizeBytes` 必须保持 `0`/`nil`——绝不能拿 0 当真实大小参与超时等计算（见 §5.7 超时预算）。

### 5.7 文件下载链 `0x0111 → 0x0114/0x0115 →（0x0112）` 🔶

```
App                                        卡
 │ ── 0x0111 {"did","fid": <目标>} ──▶
 │ ◀── 0x0114 属性帧（含【权威 size】）──────────
 │ ◀── 0x0114/0x0115 二进制块（48 KB/块）───────  逐块推送
 │ ── 0x31 ACK {"code":200}（沿用块帧 seq）──▶   （每块等 ACK，不回卡就停）
 │ …循环…
 │ ── 0x0112 {"did"} ──▶                         仅失败/取消时：终止同步
```

要点：

| 规则 | 说明 |
|---|---|
| 块大小 | 48 KB/块，逐块 ACK，**App 不 ACK 卡就停** |
| 组装 | 按序拼接为 `.dtyj` 原始容器，再转封装（§6） |
| ⛔ 超时预算 | **禁止用索引 `sizeBytes` 计算**（恒 0 → 任何 `60 + size/k` 退化成恒 60 s → 长录音在 ~30% 处断，已实测）。正确做法：收到 `0x0114` 属性帧后用真实 size 重算（参考：`60 + size/5000` 秒）；拿不到 size 就用**滚动空闲超时**（每收到一块 +60 s） |
| ⛔ 失败必须补发 `0x0112 fileSyncCancel` | 否则卡继续推块，**毒化下一条命令**的帧流 |

### 5.8 `0x0113` deleteFile（删除卡上文件）✅

| 项 | 值 |
|---|---|
| 方向 | App → 卡 |
| 请求 | `{"did":"...", "fid": <目标>}` |
| 说明 | ⚠️ 删除不可恢复；App 侧仅在其他副本确认落地后调用（如"传输后自动删除"） |

### 5.9 `0x0117` 实时音频流 ✅

**开流/停流顺序**（违反会断链）：

```
开流：0x0100 set upload_stream=1（带 did）→ 卡立刻推 0x0117 ≈50 帧/s → 再发 0x0100 start 开录
停流：必须补发 0x0100 set upload_stream=0（含看门狗强制拆流的场景），
      否则卡继续推帧无人 ACK ⇒ 约 6 秒后 CBErrorDomain Code=6 断链
```

**帧布局**（type=0x14 推送；524 帧真机抓包逐字节核对）：

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | — | 恒 `13 01`（type=0x13 + cmd=0x0117 的头两字节原样复现） |
| 2 | 1 | seq | ACK 用 |
| 4 | 4 | 载荷长 u32 BE | 帧总长 = 8 + 该值；124 B 帧 = 116，208 B 帧 = 200 |
| 8 | 4 | — | 恒 0 |
| 12 | 4 | fid u32 BE | = `0x0132` 状态里的 `fid`（会话标识） |
| 16 | 4 | — | 恒 0 |
| 20 | 4 | 递增计数 | ≈ +50/s（已收样点数，**可当时钟**） |
| 24 | 4 | 块号 | |
| 28 | 4 | 音频长度 | 84（单包帧）或 168（双包合帧） |
| 32 | 4 | — | 本固件恒 `00 00 40 A9` |
| 36 | n | Opus 包 | n/84 个包连续排列，无分隔（84 B/包，20ms@48k） |
| 36+n | 4 | 哨兵 | 恒 `5A 5A 5A 5A`，**位置 = 36 + 音频长**（⚠️ 不是固定偏移 120） |

**合法帧判定**（三者同时成立）：

```
payload.count >= 36 + length + 4
length % 84 == 0
bytes[36+length ..< 36+length+4] == 5A 5A 5A 5A
```

**208 B 合帧必须拆成两个 84 B 包**再交给下游，否则按 3 s 攒批的解码全部错位。

**流控三条铁律** ✅（2026-10-19 实时断链排查定案）：

1. **ACK 节流**：50 帧/s 逐帧 write 会饱和 iOS 发送队列（`canSendWriteWithoutResponse` 连续 false）→ 卡窗口满停发 → 看门狗重开流 → Code=6 周期性断链（30–60 s 一次）。ACK 是**位置性流控**而非可靠传输 ⇒ **每 4 帧 ACK 一次**（`ackEveryN = 4`，≈12.5 次/s）。
2. **无实时消费端时，`0x0117` 只 ACK 不入命令队列**：50 帧/s 落进命令 inbox 会把 `0x0132` 回包埋掉 ⇒ "停止/暂停按了没反应、卡却还在录"。
3. **诊断日志省着写**：逐帧 hex ≈6 KB/s，512 KB 日志两分钟轮转，会冲掉事故现场。只记计数（如每 500 帧一行）。

### 5.10 `0x000C` UT 诊断日志 ✅

卡主动推送（type=0x14），空闲时也会推（连接快照 / 插拔充电 / 按键）。**必须在推送分支即时处理，不进命令 inbox**（没人等待的报告滞留队列 = "按了卡没反应"）。

**外层布局**：

| 段 | 说明 |
|---|---|
| `5A 5A` | 魔数 |
| u16 BE = N | 记录区字节数 |
| N 字节 | 记录区 |
| 4 B 元数据 | **最低字节 = 条数** |
| `5A 5A` | 魔数 |

`stride = N / count`；实测 ≥ 20 且必须整除——**不整除直接放弃解析**（防脏数据假解析）。

**单条记录**（步长 `stride`）：

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 2 | seq |
| 2 | 6 | 设备时间 u48 BE（Unix 秒） |
| 8 | 4 | 事件 ID u32 BE（**模块在最高字节** ⚠️ 例如 `0x01000003` 是 UPTIME，不是按键） |
| 12 | 8 | value u64 BE |

**事件 ID 表**：

| ID | 名称 | 用途 |
|---|---|---|
| `0x01000006` | SYSTEM_BATTERY | 电量百分比 |
| `0x0100000C` | SYSTEM_CHARGING_CHANGED | **充电状态**（`0x0132` 无此字段，唯一来源） |
| `0x05000002` / `0x05000003` | AUDIO_RECORD_START / STOP | **录音精确计时锚点**（卡侧 Unix 时间戳） |
| `0x05000004` / `0x05000005` | PAUSE / RESUME | 暂停 / 继续 |
| `0x0A000001` | HAL_AI_CLICK | AI 按键 |
| `0x0A000006` | HAL_RECORD_CLICK | 录音键单击 |
| `0x0A000008` | HAL_RECORD_LONGPRESS | 录音键长按 |
| `0x0B000001` | AUDIO_CONTROL_REMARK_BUTTON_CLICK | **打点（要点标记）** |
| `0x0B000002` … `0x0B000005` | START/STOP/PAUSE/RESUME_RECORDING | 录音状态机 |
| `0x0C000005` / `0x0C000006` | AUDIO_INSTANCE_START / STOP | 会话起止 |
| `0x09000001` | DISPLAY_SET_STATE | 仅无参数状态；**屏幕显示无写通道**（见 §5.11） |

**录音计时校准**（两个方向都要处理）：

- 卡先开始 ⇒ 本地锚点**前移**（`adoptDeviceElapsed`）；
- App 先按、命令 300–800 ms 后才在卡上落地 ⇒ 本地锚点偏早，必须**后移**（`adoptDeviceClock`）——只在本地时长 < 10 s 时允许后移，否则报告延迟会让秒表倒跳；
- 打点偏移 = `REMARK 事件时间戳 − RECORD_START 事件时间戳`；事件批量送达不影响准确性。

### 5.11 已知但未实现 / 禁用的命令

|---|---|---|

| `0x0136` sendSysControl | 🔶 | 系统控制，未实现 |

## 附录 B：错误码总表

| code | 出现场景 | 语义 | 处置 |
|---|---|---|---|
| 200 | 所有响应 | 成功 | — |
| 405 | 任意命令 | **未鉴权**（会话丢 token） | 清鉴权标志 → 重跑 `0x0008→0x0133` → 重试原命令一次 |
| 501 | 鉴权 | 凭据不匹配 | 提示重新导入 secret，勿自动重试 |
| 502 | 鉴权 | token 形状非法 | 客户端 bug |
| 503 | 鉴权 | 字段缺失 / null | 客户端 bug |
| Code=6 | BLE 层 | 连接断开 | 多为流控被破坏的下游症状，查 §5.9 三铁律 |

## 附录 C：实现方必须遵守的规则

> 每条都对应至少一次真机事故，违反即出"编译过、零警告、点了没反应"类问题。

1. **ACK 用 `type=0x31` 且沿用推送帧 seq**；`0x13` 会被当新命令（§3.3）。
2. **帧解析先把缓冲拷成 `UInt8` 数组**再切片（Swift `Data` 切片 startIndex 偏移会越界崩溃）。
3. **卡推送（`0x0117` / `0x000C`）在推送分支即时处理**，绝不进命令 inbox。
4. **鉴权后所有命令带同一个 did**（含 `0x0100 set`）；405 按 §附录 B 恢复。
5. **实时流 ACK 节流（每 4 帧）**；拆流必须补发 `upload_stream=0`；下载失败必须补发 `0x0112`。
6. **超时不许用索引 sizeBytes**（恒 0）：用 `0x0114` 真实 size 或滚动空闲超时。
7. **`nil` ≠ 0**：secret / size 等拿不到就是 `nil` 并置灰功能，绝不拿 0 当默认值。
8. **只读边界**：不改固件/配置/绑定；禁用 `0x0004`；实验完发 `0x0134` 干净断开。

### E.3 安全边界声明（全部真机实测）

| 问题 | 结论 |
|---|---|
| 无 secret 可用的命令 | 仅 `0x0008` + `0x013F`；其余全 405 |
| 调试后门 | 不存在（先形状后密码学，无旁路分支） |
| 蓝牙刷固件 | ⛔ OTA 锁在鉴权门后 |
| secret 可否推导 | ⛔ 独立 128-bit 随机数，与 sn/mac/did/corp 零派生关系（11 种哈希组合 0 命中） |
| 挑战-应答泄露 | 不泄露（secret 永不出卡；挑战一次性） |
| secret 获取途径 | ① 卖家跑一次提取脚本（不需解绑）② 自己绑一次再解绑 ③ 拆机读 Flash（不建议） |
